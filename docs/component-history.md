# 旧设计依赖与 library/history

用户约定：2026-11-12。每次更新由用户明确选择是否保留历史。选择保留时，将旧设计依赖的元件版本、CAD 和配套资料保存在历史目录；引擎继续渲染旧工程，历史元件不供新建使用。本规则覆盖此前元件仅保留当前版及成功更新后直接删除旧资源的条款。

## 每次更新的保留选择

- 用户说“保留历史”：先冻结被替换版本及依赖到 `library/history`，核验成功后采用新版。
- 用户说“不保留”：不归档本次被替换版本，按当次范围完成更新；无需再次请求确认。不得把这次选择扩大为删除此前已明确保留的历史或其他现用共享依赖。旧几何没有保留下来时，不承诺旧设计可精确复现。
- 更新未说明选择时先确认；不能以全局默认替代当次决定。首次新增没有被替换内容时不要求选择。
- 在暂存/采用回执中记录选择及其授权依据，后续采用沿用同一事务选择，不能悄悄改成另一种模式。

命令行暂存使用 `python3 hksop.py package stage <package> --history retain` 或 `--history discard`；采用暂存包时沿用回执中的选择。替换已有定义但未指定选择会停止，暂存与采用选择不一致也会停止。该选择只适用于本次事务。

## 保存范围（选择保留时）

`library/history` 保存可追溯的历史定义、版本身份及必要资源入口，包括原单件/套件/板型定义、局部基准和变换、BOM 依赖、CAD/STEP、原加工图及镭标资料、渲染资源和已有验收记录。资源可按内容哈希去重；历史引用必须受到保护，并能随分发独立解析，不能指向某台电脑的临时目录。不要只存图片或旧 ID 而丢失实际几何、配套资料与依赖。

项目的工程 JSON 历史与元件历史分开：项目文件保留实例、位置和版本选择；`library/history` 保留这些实例所依赖的旧定义与资料。仅冻结实际依赖集合，不复制整库或恢复所有调试修订。选择保留后，无法确认某项是否为必要依赖时，先保留该项并列出未决范围。

## 更新顺序与身份

1. 记录用户当次保留/不保留选择；读取当前包、原版本标识、项目锁和已知工程引用。确定本次实际替换的定义与资源，保留原验收范围。
2. 选择保留时，在替换前冻结旧定义与依赖，登记到 `library/history`；明确不保留时跳过历史归档。验证新增历史文件可读、SHA256 一致、BOM/资源引用完整；选择保留但历史保存失败时，不得继续执行会丢失旧版的替换或清理。
3. 让新版和旧版拥有明确、可区分的身份；已被旧工程使用的 ID 不能静默指向新版几何。可以保留旧 ID 作为历史身份并为新版分配独立 ID，或使用经过验证的版本解析；具体映射必须记录。
4. 切换现用版本并构建必要索引/运行资源。历史元件可参与旧工程解析和渲染，但从新元件选择、拖放及新增入口排除；当前元件仍可正常新建。
5. 检查旧工程打开/渲染、新版新建、历史新增拒绝与资源可读性。只测试新增、变更及直接影响，未变 CAD/图纸沿用验收。最后更新日志、历史清单和本次增量交付。

工程没有足够版本信息时，只能用已核实的旧 ID、来源修订、锁文件或保存时间等证据建立兼容映射；有歧义则列为待处理，不能通过自动升级掩盖。历史元件在当前引擎中可显示，不等于实物兼容、运动性能或制造放行已验收。

## 引擎与界面要求

- “能解析/渲染”与“能新建”是独立能力。旧实例仍可载入、显示和导出已有设计；历史记录不得被当作未知元件过滤掉。
- 历史元件不显示在新建时可拖入的元件列表；拖放、点击新增及直接新增调用均需检查历史状态，不能只隐藏一张卡片。
- 打开旧工程不属于新建历史元件，不能被新增限制误拦。当前元件的选择和新增行为保持可用。
- 旧版资源和 BOM 依赖按历史定义解析，不可从新版同名文件推断几何相同。缺失资源、版本冲突或未覆盖行为明确报告。

## 清理、分发与交付

历史定义和受其引用的资源属于继续使用的依赖，不能按“未被当前目录引用”“旧文件”“更新成功”判定可删。只有核对现用、历史和项目引用后才处理本次明确无依赖的临时副本；本规则不授权批量清理。

GitHub 分发包含本次支持的历史定义及其可解析资源依赖，并采用相同的渲染/新增限制。外接盘只同步本次新增或变更文件，保留历史依赖的独立版本身份，不重新压缩整库。日志分别记录 NAS、运行目录、GitHub 和外接盘的实际状态及缺项。
